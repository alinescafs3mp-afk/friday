Советы Grok → Opus по hardening (после линии 31.07–02.08)

Пишу после чтения коммитов main за последние трое суток и архитектуры.

Цель — не пересказ того, что уже сделано, а углы, с которых ещё полезно смотреть.

Ты уже закрыла огромный пласт; ниже — то, что остаётся «тихим» или легко сломается следующим «удобным» изменением.

Закон проекта (grok/GROK.md) и измеренные пороги — выше этого файла.



1\. Главный сдвиг последних дней: решение до модели, а не после

Почти все свежие фиксы agent-loop (oversight «что писал X», напоминание, chitchat без tool-схем, «имя из графа не уходит в поисковик», приоритет архива над интернетом) устроены одинаково:

Сначала структура решает, звать ли инструмент / куда не ходить / что не поднимать. Модель получает уже готовый факт или вовсе не получает развилку.

Это теперь канон проекта, а не разовый хак. Модель в Friday — плохой арбитр намерений там, где цена ошибки — утечка, молчаливый no-op или ответ не тому человеку. Арбитр намерения и «похожие записи в архиве» уже не раз утаскивали наружу то, что должно было остаться внутри.

Куда копать дальше (высокий ROI):



Любое место, где модель сама решает «звать tool или ответить из знаний». Особенно follow-up («а сроки?», «а кто этим занимается?») — им уже передали две предыдущие реплики, но паттерн легко повторится в новом органе или новом tool.

Любой новый tool с side-effect (напоминание, запись, merge, export). Если модель «забыла позвать» — это уже не баг модели, а отсутствие structural pre-call. Прецеденты: speak вынесен за цикл, file-request распознаётся шире, oversight вызывается до хода.

Места, где арбитр намерения всё ещё видит только одну реплику. Две — минимум; для части сценариев может понадобиться «тема + текущий ход».



Как проверять: не «модель должна понять». А «если модель ответит ерунду / промолчит / уйдёт в web — структура всё равно делает правильное». Тест обязан быть зелёным при замоканном «глупом» LLM.



2\. Молчаливый обрыв / пустота / неправильный путь — класс дефекта №1

За трое суток вы поймали и закрыли один и тот же класс много раз:



документ принят, текст обрезан — человеку «стал знанием»;

голос не распознался — «загружен документ: …ogg»;

restore сорвался — база удалена, а сообщение «no previous database»;

монитор сдвинул курсор до доставки — совпадение потеряно навсегда;

research таймаут — уже загруженные источники выброшены;

to\_llm\_message режет с головы — счётчик и поздние источники исчезают;

автопроверка / grounding-предупреждение — либо всегда, либо не по делу.



Паттерн: система что-то сделала, но человек об этом не узнал, либо узнал ложную историю.

Куда копать:



Каждый \[:N], limit=, max\_chars, timeout, except …: continue, or \[], or {}, soft-fail в ingestion / bridge / organs / workers.

Любой путь, который возвращает success=True при пустом полезном результате.

Любой cursor / offset / «уже обработано», который двигается до подтверждённой доставки или до успешной записи.

Места, где «частичный результат» возможен, но наружу уходит либо полный успех, либо полный провал.



Правило, которое уже почти канон: граница обязана назвать себя.

total рядом с count, «принято только начало, страниц N», «дальше — в тексте», partial=true, strategy.rerank\_dropped, явная пометка в Telegram.

Молчаливая деградация здесь запрещена сильнее, чем «некрасивый» текст.

Тест: мутация, которая возвращает старое «тихое» поведение, обязана краснеть.



3\. Shared archive vs person: асимметрия намеренная и хрупкая

FRIDAY\_SHARED\_ARCHIVE=1 сделал документы и записи общими через подмену арендатора в одном месте (выдача актора). Переписка, напоминания, заявки, авторство решений, лента активности — личные (person\_id / own\_id).

Коммиты 02.08 показали, сколько мест эту границу не различали:



message\_search по арендатору → чужие реплики;

напоминание под общим user\_id → приходило владельцу;

«кто решил» писалось арендатором;

сводки строились по личному id и для всех, кроме хозяина, были пустыми;

фоновые циклы крутили N учёток при одном арендаторе.



Остаточный риск:



Любой новый storage-метод, который принимает user\_id, должен явно решить: это tenant (shared corpus) или person (own chat / own reminders / own activity). Одно забытое место = тихая дыра или тихая пустота.

Oversight сейчас смотрит «своих» через иерархию. Правило спит, пока нет ни одного руководителя — хорошо. Но любой новый admin-маршрут с target user\_id обязан пройти тот же \_protect\_owner\_target + иерархический фильтр.

custom\_instructions уже убрали из списка учёток. Рядом могут жить другие поля metadata\_json. Инвентарный тест на «что отдаёт list users без all\_data.read» стоит расширять при каждом новом поле.



Как проверять: матрица «actor × target × shared\_archive on/off» на каждом новом маршруте, который трогает user\_id. Не «у меня на стенде один пользователь».



4\. Tool result → модель → человек: JSON как яд

Несколько коммитов подряд чинили одно: модель пересказывала человеку служебные поля (display\_name, confidence, method, content=redacted, «отсеяны порогом уверенности», сырой JSON oversight).

to\_llm\_message() — граница. Всё, что за ней, модель может произнести вслух.

Куда копать:



Каждый tool, который ещё отдаёт в LLM «сырой» dict с внутренними ключами, score'ами, id'ами, version'ами политики.

Любой новый tool: сначала человеческая проекция, потом полный dict для логов/аудита.

Oversight уже переведён на «имя, сколько сообщений, когда, что именно». Тот же стандарт — к inbox\_list / what\_happened / list\_tags / activity.



Критерий: если вырезать из ответа модели все слова, которых не было в to\_llm\_message, смысл ответа не должен измениться. Если изменился — модель додумала из системного мусора.



5\. Время: одна шкала, и она местная

Зафиксировано несколько сдвигов суток: «в этот день», «вчера», «сегодня» считали месяц/день из local, а сравнение — в UTC (или наоборот). Тесты краснели после полуночи по Москве.

Правило на будущее:



Любая логика «сегодня / вчера / в этот день / на этой неделе» обязана использовать одни и те же helpers локального календаря пользователя.

Хранение — UTC. Сравнение окон «человеческого дня» — в локальных сутках.

Новый орган или tool с временны́м окном: сначала тест на границе полуночи и на «запись в 23:50 UTC = уже завтра / ещё сегодня» в TZ владельца.





6\. Instrumentation на развилках — не только для oversight

Коммит «след на каждой развилке предварительного вызова о человеке» — очень правильный ход. Разница «через API работает, в Telegram нет» искалась, пока не стало видно, где именно путь оборвался.

По духу (не как задача): для других критических развилок (archive vs web priority, reminder creation vs search, file → knowledge vs «уточню», speak vs text-only) — тот же стиль однострочного следа:

textbranch=archive\_first reason=rerank\_above\_threshold score=0.81

branch=skip\_tools reason=chitchat\_closed\_list

branch=oversight\_hit name=… matched=exact

Не метрики для дашборда. Именно след на развилке, чтобы следующее «не работает» сразу показывало место обрыва.



7\. Инвентарные и мутационные тесты — настоящая граница

Проект уже живёт этим (test\_bridge\_surface, test\_route\_inventory, test\_storage\_surface, owner-mutation boundaries, audit no-bodies).

Остаточный риск: новый маршрут / команда / tool / storage-метод, который не попал в inventory, молча расширяет поверхность. Дыра G11 (delegated admin → owner export) и дыра missions — ровно этот класс: механизм защиты уже был, но не был подключён везде.

При любом расширении API/команд/tools:



Сначала обновить inventory-константу и написать почему.

Потом код.

Мутация «убрать protect / убрать kind-filter / убрать tenant WHERE» обязана красить именно этот тест.





8\. Контекстное окно 32k — не «надежда», а жёсткий бюджет

Коммит perf(context) зафиксировал реальность: тяжёлый ход уже \~21k промпта + 2k ответа. Четыре меры (сжатие старых tool-result, урезание схем по типу вопроса, история по знакам, явный обрез) — правильные.

Что ещё смотреть:



Новый tool, который возвращает «полезный» JSON на 8–12k знаков, снова взорвёт бюджет. Бюджеты на один tool-result и на сумму в ленте — явные константы с комментарием «почему столько».

Research / multi-step: каждый новый источник в контексте — цена.

Системный промпт + описания tools + user\_model + legend — тоже бюджет. Любое «добавим ещё одно правило в system» — с замером токенов.



Кириллица в промптах оставлена осознанно (замер 13%, порог был 25%). Не переводить «для экономии» без нового замера.



9\. Неожиданные углы

9.1. «Работает через API, не работает в Telegram»

Почти все oversight-баги проявлялись именно так. Любая правка agent\_runtime или bridge, которая кажется симметричной, обязана иметь тест на обоих входах или явный комментарий «почему только здесь».

9.2. Дедуп и cursor до доставки

Мониторы уже починены. Тот же паттерн может сидеть в outbound\_notifications + organs, любом «уже сообщили» счётчике, voice/file dedup.

Правило: «сделано» = «доставлено или явно rejected», не «поставлено в очередь».

9.3. Имя человека как поисковый запрос

Закрыто для графа и для участников. При появлении новых источников имён (импорт, calendar, mail) тот же structural check должен их видеть.

9.4. Предупреждения, которые всегда некстати

Grounding-пометку сузили. Общий принцип: предупреждение, которое срабатывает на внешнем мире / болтовне, обесценивает те, что по делу. Новое предупреждение — сначала замер частоты ложных срабатываний на живом корпусе.

9.5. Backup / restore / mirror

Уже был сценарий «сорвавшийся restore удаляет живую базу». Порядок: snapshot → verify → mutate. Prune только по проверенным копиям.



10\. Практический порядок (линзы, не очередь)

При любом следующем изменении:



Structural pre-decision — может ли решение уйти из модели в код?

Silent boundary — есть ли limit/timeout/empty/fallback, который молчит?

Tenant vs person — какой user\_id здесь, shared или own?

Speakable tool result — произнесёт ли модель внутреннее поле вслух?

Local calendar — все ли окна в одних сутках?

Inventory + mutation — новый surface покрыт и ломается правильно?

Context budget — сколько токенов добавили и откуда забрали?



Если правка проходит все семь — она в духе текущей линии.

Если спотыкается хотя бы об один — сначала замер/доказательство, потом код.



11\. Чего я сознательно не предлагаю



Менять измеренные пороги без нового замера с заранее объявленным критерием.

Новые «умные» эвристики поверх арбитра намерения — наоборот, сужать его роль там, где структура уже может решить.

Перенос тяжёлой логики в system-prompt «чтобы модель поняла».

Красоту ради красоты.

## Дополнение Codex → Opus (03.08): разрывы между уже сильными защитами

Не повторяю линзы Grok выше. Я проверял другой класс: защита существует и сама по
себе сделана правильно, но соседний слой подаёт ей не тот субъект, не читает её
декларацию или теряет состояние между «начал» и «закончил».

Ниже сначала подтверждённые разрывы, затем способы превратить их не в очередные
точечные тесты, а в инварианты.



12\. P0: `user_id` уже не идентификатор человека, но security-код местами всё ещё
считает его человеком

В shared archive у актора теперь три разных идентичности:



`actor.user_id` — арендатор данных (один на всех);

`actor.own_id` / `person_id` — человек;

`actor.identity_id` — способ входа, то есть Telegram identity или API token.



Это хорошая модель, но типы остаются строками, поэтому неправильная строка проходит
без единого предупреждения. Проверены четыре последствия одной причины.

**12.1. Персональные allow/deny не действуют в общем архиве.**

`AuthorizationService.actor_for_user()` сначала берёт личный preset, затем кладёт в
`actor.user_id` общий tenant (`friday/permissions/__init__.py:456-472`). Но
`authorize()` читает overrides по `actor.user_id`, а не по человеку (`:499-548`).
На синтетической временной базе: у `person_a` записан явный deny
`knowledge.create`; `get_permission_overrides("person_a")` его видит, lookup по
общему tenant пуст, итоговое решение — allow от preset. То есть комментарий
«права остаются личными» сейчас верен для preset и неверен для overrides.

**12.2. Один участник может увидеть и подтвердить заявку другого.**

Заявка создаётся под `actor.user_id` (`execution_kernel/__init__.py:1137-1146`),
список и решение также scoped по `actor.user_id` (`server.py:1594-1646`). В shared
archive это одна строка для всех. Уведомление уже правильно уходит автору по
`own_id`, но сама заявка остаётся общей.

Белая проба на двух синтетических участниках одного tenant дала:



`other_person_can_list = True`;

`other_person_can_approve = True`.



Это не только раскрытие описания действия: если у второго человека есть нужная
capability, `execute_approved()` повторно авторизует уже ЕГО и исполнит чужой
payload.

**12.3. Идемпотентность чата образует межличностный replay-канал.**

`POST /api/chat` заявляет и завершает idempotency lease по
`(actor.user_id, source_ref)` (`server.py:1722-1765, 1973-1980`). Для API
`source_ref` задаёт клиент, а fingerprint не включает `own_id`. Два участника
общего tenant с одинаковыми body и `source_ref` попадают в один namespace.

На синтетической базе первый участник завершил ключ ответом с
`conversation_id=conversation-a`; второй с тем же ключом получил status `replay`
и этот conversation id. Документы у них общие, но ответы и разговоры — личные;
кэш не должен превращать одно в другое.

Тот же аудит нужен для `/regenerate`: принадлежность разговора правильно
проверяется по `actor.own_id`, но сообщения сразу после этого читаются по
`actor.user_id` (`server.py:1339-1353`). В shared archive это две разные строки,
поэтому собственный разговор находится, а собственный вопрос внутри него — нет.

**12.4. «Per-user» rate limit на деле per-tenant.**

Ключи `telegram:user:{actor.user_id}` и `api:user:{actor.user_id}`
(`server.py:819-848`) общие для всех участников shared archive. Один шумный клиент
может исчерпать бюджет всех остальных, включая владельца. Глобальный Telegram
лимит должен остаться глобальным; личный обязан считать principal, а не corpus.

Это нельзя чинить россыпью замен `user_id → own_id`: часть операций действительно
должна работать по общему corpus. Нужен явный контракт областей:



`tenant_id` — knowledge, graph, Inbox общего корпуса, retrieval;

`principal_id` — permissions, approvals, conversations, rate limits,
idempotency ответов, личные уведомления, авторство;

`credential_id` — отзыв токена, security-события конкретной сессии, но не
личность автора.



Лучший hardening — перестать принимать голый `str` на критических границах:
минимум отдельные named helpers/параметры, лучше `NewType`/value objects и один
явный переход из principal в tenant. `own_id` полезен как совместимость, но имя не
говорит вызывающему, для какого класса данных оно обязательно.

Критерий приёмки до правки:



1. Матрица `principal A/B × shared on/off`: личный deny и allow работают ровно
одинаково в обоих режимах.
2. Заявка A невидима B; list не содержит её, decide отвечает тем же 404, что
чужой id; только A может решить, а действие исполняется в общем tenant.
3. Одинаковый `source_ref` у A и B не конфликтует и не возвращает чужой response;
повтор A остаётся идемпотентным.
4. Исчерпание личного лимита A не расходует личный лимит B.
5. `/regenerate` в shared archive читает историю человека, но retrieval по-прежнему
идёт в общий tenant.
6. Audit каждого случая содержит и principal, и tenant, но не credential вместо
автора.

Мутации: подставить tenant вместо principal отдельно в каждом из шести тестов.
Каждая подмена обязана красить именно свой тест.



13\. P0: `ToolSpec.risk` объявлен, но исполнитель его не читает

Комментарий у `ToolSpec.risk` говорит правильную вещь: обязательный класс риска не
даёт новому опасному инструменту пройти fail-open (`execution_kernel/__init__.py:
542-548`). Фактический гейт, однако, читает отдельный словарь `HIGH_RISK_TOOLS` по
имени (`:524-528, 1091-1093`). Поле `tool.risk` в решении об approval не участвует.

Сейчас множества случайно совпадают: три `risk="high"` присутствуют в словаре.
Но проба с зарегистрированным синтетическим `ToolSpec(risk="high")`, которого нет
в `HIGH_RISK_TOOLS`, успешно вызвала handler без заявки:



`declared_high_executed_without_approval = True`.



Это ровно fail-open, от которого обязательное поле якобы защищает. Следующий орган
с high-tool может всё сделать «по правилам» и всё равно обойти человека.

Рекомендуемый контракт: policy живёт в самом spec/реестре и больше нигде.



Для `high` обязательны `approval_predicate`, человеческий `approval_summary` и
явный `outcome_contract`;

для `mutate` явно объявляется `idempotency`/postcondition либо причина, почему
результат unverifiable;

регистрация падает на старте, если декларация неполна;

`execute()` принимает решение только из зарегистрированного spec;

отдельные словари и `if name == ...` допустимы как реализация callbacks, но
startup-инвариант обязан доказать полное и точное соответствие.



Человеческое описание тоже часть security-контракта. Generic fallback
«Выполнить tool_name» для нового high-tool означает слепое подтверждение. Тест
должен требовать, чтобы два payload, различающиеся материальным полем, давали
различимые summary, а внутренние id не были единственным объяснением.

Мутация: зарегистрировать high-tool без predicate или summary. Ожидается отказ
регистрации/старта; handler не должен стать достижим ни при каком preset.



14\. P0: для обычного mutator нет состояния «эффект мог случиться»

Approved high-path уже различает `failed` и `uncertain`, заявляет действие атомарно,
сверяет payload hash и проверяет postcondition. Обычная ветка `execute()` слабее:
handler вызывается, потом пишется audit; `TimeoutError` превращается просто в
`Tool execution timed out` (`execution_kernel/__init__.py:1095-1120`).

Две синтетические пробы подтверждают разрыв:



mutate-handler записал эффект и затем поднял `TimeoutError` — эффект есть,
`success=False`, наружу только «timed out»;

handler закоммитил запись и затем процессно оборвался через `BaseException` —
эффект сохранился, строк `tool.invoke` ноль, потому что audit пишется только после
возврата handler (`:1440-1470`).



Особенно опасна отмена `asyncio.to_thread`: await уже отменён, а поток может
продолжить SQL/файловую операцию. Называть это обычным отказом — приглашение к
повтору.

Нужен единый durable invocation lifecycle не только для high-tools:



1. До dispatch записать append-only `tool.invoke.started` с `invocation_id`,
principal, tenant, tool, policy decision id и безопасным fingerprint аргументов.
2. После dispatch завершить отдельным событием `succeeded`,
`failed_before_effect` или `uncertain`. Не обновлять первый audit-row: оборванная
пара сама является доказательством незавершённости.
3. Любая отмена/таймаут/потеря процесса после dispatch для `mutate/high` —
`uncertain`, если отдельная idempotency + postcondition не доказали обратное.
4. Автоповтор разрешён только если spec объявляет стабильный idempotency key и
наблюдаемое postcondition. «Handler бросил Exception» недостаточно, чтобы доказать
отсутствие эффекта.

Отдельная дыра рядом: одинаковая активная заявка не дедуплицируется. Два
`create_action_approval()` с одним principal/tool/payload_hash/policy_epoch создали
два разных id и две pending-строки. Текст модели «не повторяй» — не защита, а
уведомления дедупятся по approval id, поэтому оба тоже различны.

Нужна уникальность только для **активной** попытки; после rejected/expired/done
человек вправе сознательно запросить то же действие заново. Проверить одновременно
два запроса из разных потоков: одна active approval, одно уведомление, один effect.

Crash-matrix для приёмки:



до durable start;

после start, до handler;

после эффекта, до возврата handler;

после возврата, до terminal audit;

во время postcondition;

во время ответа Telegram/API.



На каждой точке: не больше одного эффекта, start видим, неизвестность названа,
автоматического повтора нет. Мутация «uncertain → failed» обязана красить
state-machine тест.



15\. P1: `policy_epoch` сейчас константа, а не эпоха политики

Approval-path хранит и сравнивает `policy_epoch`, а комментарии называют это
повторной авторизацией. Но полный поиск по `friday/` показывает единственный
источник значения: `ActorContext.policy_epoch: int = 1`
(`permissions/__init__.py:38-45`). `actor_for_user()` эпоху из storage не загружает;
grant/deny/revoke/preset/status её не увеличивают. Storage-тест сравнивает вручную
переданные `epoch-1` и `epoch-2`, но интеграционный контур всегда передаёт `1`.

Повторная `authorization.require()` всё же спасает простое снятие capability
(кроме shared-override дефекта из §12), поэтому это не утверждение «все отозванные
права исполняются». Разрыв другой: заявленная защита от смены policy не существует,
а тест доказывает helper, не систему.

Варианты контракта:



per-principal auth epoch, атомарно увеличиваемая при preset/override/status;

отдельный runtime policy hash/epoch для изменения risk registry и правил approval;

в заявке фиксируются оба, claim сверяет оба непосредственно перед dispatch.



Интеграционный тест: создать approval через настоящий kernel, изменить policy через
настоящий admin/service route, построить нового actor и доказать, что старую заявку
нельзя claim. Мутация «не увеличить epoch» должна краснеть. Если эпоха после
повторной require признана избыточной — удалить обещание и мёртвый механизм, а не
оставлять security theatre.



16\. P1: exception text — такой же недоверенный payload, как tool result

Обычная ветка отдаёт пользователю только тип исключения. Approved-path сохраняет в
`action_approvals.error` полную строку `f"{type}: {exc}"`, а `/api/me/approvals`
возвращает запись целиком (`execution_kernel/__init__.py:1310-1337`,
`server.py:1594-1646`). Exception стороннего клиента может содержать URL с query
token, Authorization header, абсолютный путь или кусок документа.

Синтетический handler поднял:



`RuntimeError("credential=SYNTHETIC_VALUE at C:/example/path")`.



Наружный `ToolResult` был безопасным (`Tool failed: RuntimeError`), но durable
approval-row сохранил всю строку дословно. Logger также получил её со stack trace.

Нужен центральный error contract:



durable/user-visible поля — reason code, тип, безопасная локализованная фраза,
correlation id;

секреты, URL credentials/query, абсолютные пути и содержимое проходят один общий
sanitizer до любого persistence/Telegram/API;

полный traceback допустим только в локальном operator sink с явно принятой
политикой, но bearer/token нельзя печатать и туда;

ошибка sanitizer сама fail-closed: generic reason, не исходная строка.



Тест подавляет synthetic token, путь, email и фрагмент документа во всех четырёх
поверхностях: approval row, API JSON, Telegram notification/reply, audit/log capture.
Мутация, возвращающая `str(exc)`, должна красить тест.



17\. Проверять не endpoint'ы по одному, а одну операцию через все поверхности и
все допустимые перестановки

Последние регрессии показывают, что локальные тесты сильные, а расхождение живёт
между слоями. Полезен маленький differential/state-machine harness поверх уже
существующих fixtures.

Для одной операции (approval, reminder, regenerate, review decision, cancel
mission) выполнить эквивалент через:



прямой service/kernel;

HTTP route;

signed Telegram bridge/callback, если поверхность существует.



Сравнивать не тексты, а post-state: principal/tenant строку, effect count, audit,
notification recipient, terminal status и отсутствие чужой видимости.

Затем переставлять события: double click, два параллельных запроса, revoke между
approve и claim, expiry одновременно с decide, cancel одновременно с worker tick,
shutdown после commit. Для approvals это естественный `RuleBasedStateMachine`:
`pending → approved/rejected/expired → claimed → done/failed/uncertain`, все
обратные и боковые переходы запрещены.

Главные инварианты state-machine:



terminal state не открывается снова;

effect count ≤ 1;

чужой principal не различает «нет id» и «id чужой»;

смена policy делает старую попытку неисполняемой;

started без terminal становится видимой `uncertain`, а не исчезает;

ответ «готово» появляется только после postcondition.



Это поймает следующий обход класса, а не только сегодняшний route.



18\. Hardening самого hardening-процесса: инструкции уже дрейфуют от main

Сейчас `sol/SOL.md` говорит «схема 18», а `friday/storage/_base.py` объявляет 24.
Там же quality gate вызывает `.venv/bin/...` по пакету `jericho`, которого в
актуальном `origin/main` уже нет; `sol/BRIEF_PORTING.md` фиксирует 15 инструментов,
актуальный реестр содержит 25.

Это не косметика. Исполнитель, буквально следующий закону, либо не запустит gate,
либо проверит не тот пакет; архитектурное решение может опираться на старую схему
и старую поверхность.

Нужна одна исполняемая команда quality gate (`tools/...` или project task), которая
сама знает текущий package path и одинаково вызывается на Windows/Linux. Документы
ссылаются на неё, а не копируют список команд. Для чисел, являющихся контрактом
(schema version, tool inventory), тест либо сверяет документ с кодом, либо документ
вообще не замораживает быстро меняющееся число.

Критерий: чистый checkout выполняет одну документированную команду без ручного
перевода путей; намеренная смена `SCHEMA_VERSION` или состава registry красит
contract test, пока связанное описание не обновлено.



19\. Рекомендуемый порядок для Opus



Сначала §12: это уже воспроизводимые межличностные auth/replay/approval разрывы,
а не гипотеза.

Затем §13: сделать risk-декларацию исполняемой до появления следующего tool.

Потом §14 единым lifecycle, иначе каждый новый mutator размножит семантику
timeout/retry/audit.

§15–16 закрыть тем же проходом по approval-path.

После этого зафиксировать всё differential state-machine из §17 и починить
исполняемый gate §18.



Не начинать с рефакторинга имён по всему репозиторию. Сначала пять красных
синтетических воспроизведений и заранее объявленные инварианты; затем самый узкий
общий контракт, который делает их зелёными. Иначе велик риск красиво переименовать
`user_id`, сохранив те же перепутанные области.
