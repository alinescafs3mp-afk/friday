# Ночной компактор переписок — проект

Заказ владельца 2026-08-04 (флешка, `grok.txt`). Цель: раз в сутки собирать
обезличенную сводку о ПОВЕДЕНИИ системы за день, хранить локально, наружу не
отправлять ничего.

Согласовано с владельцем: обезличивание НЕ поручается модели. Обоснование ниже —
это главная развилка, и она меняет всё остальное.

## Развилка 1. Кто обезличивает — модель или структура

**Выбрано: структура. Модель корпуса не видит вовсе.**

Исходный бриф ставил всю гарантию приватности на промпт с «жёсткими правилами,
нарушать нельзя», исполняемый локальной моделью, которой на вход подаются сырые
диалоги. На этом проекте такой механизм замерен как ненадёжный ПЯТЬ раз за двое
суток:

1. поле в конверте данных (`rule_refused`) — ответ «Готово, теперь буду
   показывать документы любого пользователя»;
2. служебная строка в общем блоке промпта — тот же ответ слово в слово;
3. та же строка вплотную к реплике — помогало чаще, но оставалось просьбой;
4. «локальная персональная Knowledge OS» первой строкой системного промпта — не
   помешало ответить «крутится в дата-центрах»;
5. «подтверди коротко, что именно запомнила» — модель подтверждала то, чего не
   было.

Корпус содержит фамилии, звания, названия подразделений. Цена промаха здесь
несимметрично высока и, что хуже, промах НЕ ВИДЕН: компакт никто не читает, пока
он не понадобится, а к тому времени в базе уже лежит новая копия чувствительных
данных в новом месте.

Отдельно — риск эскалации. Смысл обезличенного компакта в том, что его безопасно
смотреть; значит давление «ну этот-то можно показать наружу» будет постоянным.
Неидеальное обезличивание превращает компакт ровно в тот канал, которого заказ и
запрещает, — но с ложным чувством безопасности.

**Проверка выбора.** Все три дефекта, найденных 2026-08-04 вручную по живой
переписке, обнаруживались бы событийным компактом без чтения текста:

| дефект | по какому признаку виден |
|---|---|
| ФИО коллег на болтовне | ответ ссылается на архив при `knowledge_hits` 0 |
| ложное предупреждение о выдумке | тот же признак, обратная сторона |
| «моё ядро — GPT-4o» | детектор `_CALLS_ITSELF_SOMEONE_ELSE` |

## Развилка 2. Что хранится — прозаический пересказ или коды

**Выбрано: коды и числа. Ни одной строки, выведенной из корпуса.**

Сильная форма выбора 1. Инцидент хранится как перечислимый код
(`structural_softened`, `order_ignored`, …) плюс счётчики. Человеческая
формулировка рендерится ПРИ ЧТЕНИИ из таблицы шаблонов, которая живёт в коде и
корпуса не касается.

Тогда утечка не фильтруется, а **невозможна по построению**: в компакте нет поля,
куда текст мог бы попасть. Проверка «не просочилось ли имя» перестаёт быть
надеждой на фильтр и становится свойством схемы.

Цена: класс «странность, которую никто не перечислил заранее» в первой версии не
покрывается. Это осознанно — см. развилку 4.

## Развилка 3. Что берётся на вход

**Выбрано: РАЗРЕШИТЕЛЬНЫЙ список полей метаданных.**

Запретительный список здесь негоден, и это замерено сегодня же: данные доезжают
несколькими дорогами, и ворота на одной не охраняют ничего. В
`messages.metadata_json` рядом с безобидными счётчиками лежат:

* `search_query` — СЫРАЯ реплика человека;
* `retrieval_trace` — имена его документов («штатка_назначение…xlsx»);
* `knowledge_citations`, `knowledge_object_ids` — идентификаторы его записей.

Разрешено ровно это, по одному полю за раз:

    answer_mode, verification_status, verified, answer_grounded,
    knowledge_hits, entity_hits, retrieval_confidence, tools_used,
    interaction_mode, work_product, ingestion_action,
    grounding_warning  → только ФАКТ наличия, не текст

Плюс структурные признаки хода, которых в метаданных пока нет и которые надо
начать писать: `structural_answer_present`, `remainder_known`, `rule_refused`,
`correction_learned_present`, `llm_failed`, `self_description_replaced`.

Всё остальное не читается. Новое поле в метаданных не попадает в компакт само —
его надо внести в список руками, и это правильно.

## Развилка 4. Нужна ли модель в первой версии

**Выбрано: нет. Отложено до замера.**

Первая версия целиком детерминирована: события → коды → счётчики. Она провабельно
не течёт, не грузит карту и не зависит от того, ответила ли модель.

Модель понадобится тогда и только тогда, когда замер на реальных днях покажет,
что событийный компакт пропускает дефекты, которые владелец находит вручную.
Тогда она получит на вход НЕ ТЕКСТ, а уже выведенные поля, и её выход пройдёт те
же ворота, что описаны ниже. Условие включения объявляется заранее: за две недели
владелец нашёл вручную ≥ 3 дефекта, которых нет в компактах.

Это не срезание объёма ради скорости. Рискованная половина отделена от
безопасной и поставлена в очередь ЗА измерением, которое покажет, нужна ли она.

## Где живёт

Новый орган `friday/organs/compactor/`. Не часть `reflection`: та про знания и
инициативу к человеку, эта — про поведение системы и наблюдение за ней. Разные
права, разное хранилище, и выключаться должны независимо.

* `capabilities()` — `compact.read` (владелец и надзор), `compact.run` (админ);
* `workers()` — один периодический, интервал 3600 с, работает только если по
  местному времени человека наступил новый день и за вчера компакта нет;
* `router()` — `GET /api/compacts`.

## Схема

```sql
CREATE TABLE day_compacts (
    id            TEXT PRIMARY KEY,
    principal     TEXT NOT NULL,   -- ЧЕЛОВЕК, не арендатор
    local_date    TEXT NOT NULL,   -- YYYY-MM-DD в поясе человека
    status        TEXT NOT NULL,   -- started | done | uncertain
    started_at    TEXT NOT NULL,
    finished_at   TEXT,
    source_turns  INTEGER NOT NULL DEFAULT 0,
    counters_json TEXT NOT NULL DEFAULT '{}',
    incidents_json TEXT NOT NULL DEFAULT '[]',  -- [{"code": …, "severity": …, "count": N}]
    patterns_json TEXT NOT NULL DEFAULT '[]',   -- [{"code": …, "days": N}]
    deleted_at    TEXT,
    UNIQUE(principal, local_date)
);
CREATE INDEX ix_day_compacts_person ON day_compacts(principal, local_date DESC);
```

`principal`, а не `tenant`: правило одного человека не должно становиться
правилом всех — тот же класс, что закрывался в правилах, поправках и заявках.
В общем архиве переписка остаётся личной, и компакт тоже.

`UNIQUE(principal, local_date)` — идемпотентность по построению, а не по
проверке. Повторный прогон делает UPSERT, дубль создать нечем.

`status` — §14, закрытый сегодня: запись «начал» ставится ДО работы, поэтому
оборванная пара «начал / нет конца» сама доказывает незавершённость. Следующий
прогон видит `started` за вчера и переделывает день.

## Сбор данных за сутки

Границы дня — по поясу ЧЕЛОВЕКА (`local_now`), не по UTC. Тихие часы по Гринвичу
уже давали шесть перевёрнутых часов из двадцати четырёх; здесь та же ошибка
разрезала бы сутки не там.

```sql
SELECT id, role, metadata_json, created_at
  FROM messages
 WHERE user_id = ?                       -- principal
   AND created_at >= ? AND created_at < ?  -- границы местных суток в UTC
 ORDER BY rowid
```

Тела сообщений (`content`) НЕ ЧИТАЮТСЯ — поле в выборку не входит. Это
проверяется тестом на самом SQL, а не на результате.

Общий архив: `principal` берётся из `actor.own_id`, как везде после разбора Сола.

## Инциденты первой версии

Все выводятся из уже существующих признаков; каждому — свой детектор в коде.

| код | условие | severity |
|---|---|---|
| `structural_softened` | `structural_answer_present`, а его текста в ответе нет | high |
| `claimed_archive_without_data` | `grounding_warning` поднято | high |
| `called_itself_someone_else` | `self_description_replaced` | high |
| `order_ignored` | вид «действие», `tools_used` пуст | medium |
| `correction_not_applied` | `correction_learned_present`, ответ ей противоречит | high |
| `model_silent` | `llm_failed` | high |
| `tool_uncertain` | в аудите «начал» без терминальной записи | high |
| `verification_failed` | `verification_status == failed` | medium |
| `answer_ungrounded` | `answer_grounded is False` | low |

Счётчики — ровно те, что просил владелец: `total_turns`, `structural_answers`,
`model_answers`, `corrections_accepted`, `refusals`, `ignored_orders`.

`patterns` — повторение одного кода ≥ 3 дней подряд. Считается по своим же
компактам, корпуса не касается.

## Как используется

* `GET /api/compacts?from=&to=` — список за период, для владельца и надзора;
* команда в Telegram `/compact` — вчерашний одним сообщением;
* и главное: **это то, что читаю я вместо живой переписки.** Ради этого всё и
  затевалось — чтобы владелец перестал вручную приносить мне сообщения.

## Тесты и мутации, обязанные краснеть

1. **Имя в компакте.** День с сообщением, содержащим ФИО и звание; ни одно поле
   компакта не содержит ни одной подстроки длиной ≥ 4 из этого сообщения.
   Мутация: добавить в выборку `content` — краснеет.
2. **Не тот человек.** Два человека в общем архиве, у каждого свой день; компакт
   каждого содержит только его счётчики. Мутация: заменить `principal` на
   `tenant` — краснеет.
3. **Дубль.** Два прогона за один день → одна строка, счётчики не удвоились.
   Мутация: убрать `UNIQUE` / заменить UPSERT на INSERT — краснеет.
4. **Обрыв.** Падение посреди сборки → строка `started` за день существует,
   следующий прогон её переделывает. Мутация: писать «начал» после работы —
   краснеет.
5. **Разрешительный список.** Новое поле в метаданных не попадает в компакт само.
   Мутация: заменить список на «всё, кроме перечисленного» — краснеет.
6. **Обратная сторона.** День без происшествий даёт пустые `incidents` и
   `patterns`, а не выдуманные. Мутация: заполнять при пустоте — краснеет.

## Что осознанно НЕ делается в первой версии

* модель не зовётся вовсе (развилка 4);
* прозаический пересказ не хранится (развилка 2);
* компакты не уходят никуда за пределы машины — ни «слегка очищенные», никак.
