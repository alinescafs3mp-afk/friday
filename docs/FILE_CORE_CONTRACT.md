# Базовый файловый контур Friday

Статус: обязательный рабочий договор, 2026-08-12. Этот документ нельзя считать
выполненным только по unit-тестам: завершение требует проверки на развёрнутой
Friday.

## Приоритет

Простота и надёжность важнее универсального роутинга. Базовая цепочка:

`запрос → SQLite → точный Raw/набор Raw → проверенные байты на диске → парсер → операция/ответ`

Модель не выбирает файл, не выдаёт разрешение на чтение и не решает, надо ли
обращаться к диску. Dense-модель используется только для свободной формулировки
ответа по уже выбранным и прочитанным источникам.

## SQLite как оперативная память файлов

SQLite хранит и связывает:

- владельца/отправителя и tenant;
- Raw Object, источник и все устойчивые транспортные алиасы;
- Telegram-сообщение, reply, ответ Friday и фактически показанные цитаты;
- зарегистрированный относительный путь, размер и SHA-256;
- состояние извлечения, полноту и тип содержимого;
- активный набор файлов каждого хода диалога.

`stored_path` сам по себе не является источником полномочий. После выбора Raw
файл открывается только через зарегистрированный путь внутри files root, как
обычный файл без symlink-follow, с проверкой размера и SHA-256. Эти проверки не
являются мешающей «перестраховкой»: они доказывают, что прочитан именно выбранный
файл. Общие классификаторы, граф, архивный retrieval, арбитры и полный набор
инструментов в чистом файловом чтении запрещены.

## Обязательные источники

Одинаковый контур обязан работать для:

1. файла, приложенного в текущем сообщении;
2. ранее загруженного файла по точному имени или однозначному описанию;
3. немедленного продолжения «этот файл / в нём / последний пункт»;
4. Telegram reply на исходное сообщение с файлом;
5. reply на ответ Friday, который реально использовал файл;
6. фактически показанной цитаты `[K…]`: цитата должна вести к её Raw и снова
   проходить текущую авторизацию/проверку диска;
7. нескольких приложенных, названных или процитированных файлов — для общего
   резюме, сравнения и точечного поиска по всему выбранному набору;
8. явного MCP/workspace inbox — как отдельного источника, без подстановки
   одноимённого upload-файла.

Если источник не определён однозначно, Friday просит уточнение. Она никогда не
подставляет «последний файл», похожее имя или ambient-memory ответ вместо явно
указанного источника.

## Простые операции без модели

Кодом выполняются как минимум:

- подтверждение регистрации голой загрузки;
- технические метаданные;
- точная цитата/копирование доказанного литерала;
- последний пункт полного однозначно выбранного документа;
- список найденных файлов и запрос уточнения при неоднозначности;
- отказ для произвольного host-path или отсутствующего права.

Голая загрузка не запускает авторезюме. Ответ должен сразу подтвердить:
регистрацию в SQLite, проверку байтов на диске, результат парсера и сохранённую
связь с сообщением. Следующий вопрос использует этот же Raw.

## Свободный вопрос по содержимому

После выбора и проверки источников модель получает только:

- текущий вопрос;
- точные имена выбранных файлов;
- извлечённый/спроецированный текст этих файлов;
- честные признаки полноты или advisory OCR.

Она не получает ambient Knowledge Objects, граф, случайную историю, source
search или схемы инструментов. Для 2+ файлов набор сначала полностью доказывается;
потерянный участник набора означает уточнение/UNKNOWN, а не частичное резюме,
выданное за полное.

## Workspace/MCP

Явная фраза `MCP inbox`/`workspace inbox` выбирает только этот контур.
`list/search/read` выполняются детерминированно до модели. Basename открывается
только при полном поиске и ровно одном casefold/NFC-точном совпадении; иначе
Friday просит относительный путь. Абсолютные пути, `file://`, `~`, drive/UNC и
traversal не открываются. Без явного workspace-маркера basename остаётся
поиском среди зарегистрированных upload-файлов.

## Историческое владение

Владелец системы явно подтвердил 2026-08-12:

- большой исходный архив, импортированный через Opus, принадлежит владельцу;
- остальные файлы загружались владельцем либо JBL;
- строки с уже явным JBL/другим uploader нельзя переписывать;
- отсутствующий uploader у Opus-импорта можно восстановить только по точному
  признаку `import_source_path`, с предварительным backup, dry-run, ожидаемым
  количеством, транзакцией, audit row и post-integrity check;
- legacy Telegram attribution допускается только по однозначной структурной
  связи chat/message/user, без догадки по имени или содержимому.

## Зафиксированный реальный сбой 2026-08-12

Последний ход перед остановкой bridge: `БЧС.xlsx`, 26 225 байт. SQLite записала
Raw, uploader и указатель сообщения; зарегистрированный файл существует с
режимом `0600`; размер и все SHA-256 совпали; парсер сохранил 9 063 символа без
обрезки. Runtime выбрал ровно этот Raw (`expected=1`, `readable=1`, coverage
complete), но backend-authored голая загрузка была ошибочно направлена на
модельное авторезюме. Модель не ответила за 90 секунд, поэтому человек получил
fallback. Это не сбой регистрации/диска/парсера; зависимость подтверждения
загрузки от модели должна быть удалена.

Telegram bridge остановлен пользователем на время ремонта и не должен быть
поднят до согласованного развёртывания исправленного контура.

## Проверка и условие завершения

Не устраивать широкие рекурсивные батареи на каждый фикс. Цикл работы:

1. один уникальный продуктовый сценарий;
2. минимальный фикс;
3. необходимые узкие тесты и static checks;
4. следующий уникальный продуктовый сценарий;
5. после устойчивой зелени — две уникальные продуктовые батареи подряд.

Каждый запуск использует новые имена, маркеры, refs, сообщения и байты. Обязательная
финальная проверка на работающей Friday охватывает регистрацию SQLite+диск+SHA,
текущий файл, старый файл, reply, фактическую цитату, 2+ файла, поиск внутри,
последний пункт, коллизию workspace/upload и отрицательные неоднозначные случаи.

Работу/goal запрещено завершать, пока эта цепочка не работает целиком на
развёрнутом продукте. Unit-тест или зелёный отдельный D10 не является
достаточным доказательством.
