# Changelog

## 0.70.0 — 2026-07-27

0.70.0 — ключ эмбеддингов не наследовался, и проверка это благословляла: она резолвила конфигурацию иначе, чем проверяемый код.

### Fixed

- **Пустое значение — это значение, а не отсутствие.** `os.environ.get("JERICHO_EMBEDDINGS_API_KEY", <ключ LLM>)` подставляет запасной вариант только когда переменной **нет**. Строка `JERICHO_EMBEDDINGS_API_KEY=` в env-файле задаёт пустое значение, поэтому наследование не срабатывало: бэкенд эмбеддингов уходил **без заголовка авторизации**, получал 401 на каждый запрос индексации, и корпус тихо оставался без векторов.
- **`model-check` при этом показывал эмбеддинги зелёными** — он резолвил ключ через `or`, то есть считал пустое отсутствующим. Проверка, разрешающая конфигурацию **не так**, как проверяемый код, благословляет сломанную настройку. Теперь проба аутентифицируется ровно тем, чем аутентифицируется `EmbeddingBackend`, и на это есть отдельный тест.
- Наследование починено там, где ему место — в загрузке настроек: пустое значение теперь равнозначно отсутствующему.

### Как это нашлось

`jericho events` показал `worker.recovered` для советов модели, но векторов не появилось. Дальше — состояние воркера в `runtime_kv` и 401 в логе. Без журнала это выглядело бы как «эмбеддинги включены, но поиск не улучшился» — то есть как неудача векторного поиска, а не как отсутствующий заголовок.

### Compatibility

- Схема БД не меняется (**16**), зависимостей ноль. Поведение при **непустом** `JERICHO_EMBEDDINGS_API_KEY` прежнее.
- Suite: **701 тест** (+2); ruff/ruff format/mypy(101) ✓.

## 0.69.0 — 2026-07-27

0.69.0 — таймаут воркера больше не оставляет за собой работающий поток, поверх которого начинается следующий запуск.

### Fixed

- **Последний из трёх старых долгов: непрерываемый `asyncio.to_thread`.** Отмена ожидания — а таймаут воркера делает именно это — прекращает *ожидание* и больше ничего: прервать работающий поток в Python нечем. Работа продолжается, держа своё соединение с базой, а супервизор считает запуск завершённым и по расписанию начинает следующий.
- **Измерено до исправления:** блокирующий вызов на 7 секунд под пятисекундным таймаутом давал **два одновременных потока**, причём задача отчитывалась как `running`, пока осиротевший поток предыдущего тика ещё писал. Два запуска одного воркера на одной SQLite — не теоретическая тревога.
- Счётчик ведётся **внутри потока**: это единственный наблюдатель, переживающий отмену. Взгляд событийного цикла — ровно тот взгляд, который неверен. Имя задачи приходит через контекстную переменную, потому что `to_thread` копирует контекст в поток.
- Все 13 отгрузок в воркерах переведены на обёртку. Супервизор перед стартом проверяет, не осталось ли незавершённой работы, и **пропускает тик**, публикуя статус `skipped` — молчаливый пропуск был бы заменой одной невидимой проблемы на другую.
- Вне воркера обёртка ведёт себя ровно как `asyncio.to_thread`.

### Замеренное

Пик одновременных потоков: **2 → 1**. Статус задачи после таймаута: `running` → `timeout`.

### Compatibility

- Схема БД не меняется (**16**), зависимостей ноль, публичная поверхность прежняя. Новый внутренний модуль `jericho/workers/_blocking.py`.
- Suite: **699 тестов** (+5); ruff/ruff format/mypy(101) ✓. Прогон вырос до 40s: воспроизвести гонку быстрее нельзя — супервизор поднимает любой таймаут минимум до пяти секунд.

## 0.67.0 — 2026-07-26

0.67.0 — фоновый воркер перестал сжигать весь бюджет на недоступном эндпоинте. Найдено журналом событий в первый же день его работы.

### Fixed

- **`inbox_model_advice` проходил все 50 материалов по мёртвому эндпоинту.** Цикл берёт до 50 pending и останавливается после **двух успехов** — а когда эндпоинт недоступен, успехов не бывает, и он честно доходил до конца, прогоняя каждый материал через три ретрая модели с backoff. Наблюдалось на этом инстансе: 46 одинаковых ошибок в логе и упор в восьмиминутный таймаут воркера.
- Пропало впустую всё: пакет всё равно не мог отработать, бюджет цикла был потрачен, а эндпоинту, которому и так плохо, досталось ещё пятьдесят раундов трафика.
- Теперь после **трёх подряд** отказов пакет прекращается: столько подряд — это эндпоинт, а не документы. Изолированный отказ по-прежнему перешагивается, один битый файл не лишает очереди остальные сорок девять; признак — именно последовательность, и успех её сбрасывает.
- Проверено мутацией: без исправления тест сообщает «прошёл 50 материалов по мёртвому эндпоинту», с исправлением — 3.

### Как это нашлось

Журнал событий, добавленный в 0.60.0, записал `worker.failed` с `error_type=TimeoutError`. Без него сбой остался бы в логе среди прочего и не попался бы на глаза: воркер отступает с backoff и внешне ведёт себя нормально.

### Compatibility

- Схема БД не меняется (**16**), зависимостей ноль, публичная поверхность прежняя. Ограничение работы за цикл (два успеха) не изменилось.
- Suite: **693 теста** (+5); ruff/ruff format/mypy(100) ✓.

## 0.66.0 — 2026-07-26

0.66.0 — конфликты читаются по ключу, а не перебором; мост наконец пишет в журнал событий.

### Fixed

- **`store_knowledge_conflict` возвращал не ту строку, которую записал.** Он отвечал на вопрос «что я только что сохранил?» перечитыванием до 5000 конфликтов и перебором в Python — причём сравнивал по `pair_key`, тогда как строка уникальна по **тройке** `(user_id, pair_key, conflict_type)`. Если для одной пары объектов существовали конфликты двух типов, возвращался тот, у кого выше уверенность, а не только что записанный: вызывающий сообщал о противоречии, которого не находил. Теперь чтение по полному уникальному ключу, левым префиксом уже существующего индекса — миграция не нужна.
- Вторая половина — стоимость: O(n) на **каждую** запись, а обнаружение конфликтов идёт на каждый продвинутый объект. То есть тем дороже, чем ценнее становится база. Тест на это есть, и он проверен мутацией: на старой реализации падает именно тест корректности.

### Added

- **Мост пишет в `runtime_events`.** Раньше он не мог: отдельный процесс, своя SQLite, до бэкенда — по подписанному HTTP. Из-за этого недоставало ровно тех событий, которые нужнее всего: обрыв туннеля на этой машине дал **295 подряд** сбоев long-polling за трое суток, и разбирать это пришлось грепом по логу.
- Те же переходы, а не тики: 295 сбоев подряд — это **два** события (`bridge.poll_failed`, `bridge.poll_recovered`), а не 295. Отдельно покрыт исходящий цикл.
- Путь записи намеренно узкий: `POST /api/events` только для моста, **фиксированный словарь** типов событий, ограниченная нагрузка (12 ключей × 200 символов). Журнал ограничен 2000 записей — неограниченный писатель вытеснил бы из него всё настоящее простым потоком.
- **В событие уходит тип исключения, но не его текст.** Ошибка HTTP-клиента несёт полный URL, а URL Telegram несёт токен бота. На это отдельный тест.
- Журналирование не может уронить цикл, за которым наблюдает, и молчит, если подписаться не от кого.

### Compatibility

- Новый эндпоинт: **136 операций** (было 135). Схема БД не меняется (**16**), зависимостей ноль. Новый публичный метод хранилища `get_knowledge_conflict_by_pair`.
- Suite: **688 тестов** (+19); ruff/ruff format/mypy(100)/node --check ✓.

0.65.0 — плотный поиск подключён и измерен: **recall@10 0.583 → 0.833**. Категория, стоявшая на нуле, ожила.

### Измеренное — главное

Тот же стенд, те же 620 документов и 24 золотых запроса, изменилось только наличие эмбеддингов (`qwen3-embedding-0.6b`, 1024 измерения):

| категория | без эмбеддингов | с эмбеддингами |
|---|---|---|
| **cross-script** | 0.000 | **0.500** |
| **synonym** | 0.400 | **0.800** |
| **paraphrase** | 0.500 | **0.833** |
| literal | 1.000 | 1.000 |
| lexical | 1.000 | 1.000 |
| **итого recall@10** | **0.583** | **0.833** |

Две последние строки значат не меньше первых: плотный поиск **не сломал то, что лексический уже умел** — это главный риск гибридного ранжирования, и он не реализовался. Промахов 4 из 24 вместо 10.

### Fixed

- **Стенд не передавал бэкенд эмбеддингов в поиск.** Первый замер с включёнными эмбеддингами дал **побайтово тот же** 0.5833 — и это было единственным признаком: настройка говорила «включено», `HybridSearcher` получал `storage`, но аргумент `embeddings` не передавался никогда, а корпус не индексировался вовсе. Сдвинься число хоть немного — я бы поверил. Теперь бэкенд передаётся, а индексация переиспользует **производственный воркер** `_embeddings_index_all`, а не собственную версию того же: стенд, который эмбеддит по-своему, измеряет несуществующий конвейер.
- **`model-check` не проверял размер пакета.** Он слал один вход, получал 200 и рапортовал «1024 измерения», тогда как индексатор шлёт пакетами и падал на каждом запросе с `422: batch size 64 > maximum allowed batch size 32`. Корпус молча оставался без единого вектора, а поиск показывал ровно то же, что без эмбеддингов — неотличимо от «эмбеддинги не помогли». Добавлена проба пакетом того размера, каким ходит индексатор, с дословной передачей сообщения сервиса и указанием, какую настройку менять.

### Замеренное попутно

- Пропускная способность сервиса **линейна по размеру пакета**: 26 векторов/с при пакете 32 и 25/с при 256. Больший пакет экономит round-trip, но не время — сервис считает последовательно.
- Индексация 620 объектов: 281s. Чанков ноль — документы короче порога `JERICHO_EMBEDDINGS_CHUNK_CHARS`.

### Compatibility

- Схема БД не меняется (**16**), зависимостей ноль. Изменения в `tools/` и одна новая проба в `model-check`.
- Suite: **669 тестов** (+2); ruff/ruff format/mypy(99) ✓.

## 0.64.0 — 2026-07-26

0.64.0 — `doctor` ищет учётные данные Jericho в посторонних файлах. Плюс документация на всё, что появилось сегодня.

### Added

- **Проверка гигиены секретов** в `jericho doctor` и в sentinel. Повод конкретный: живой токен Telegram-бота двое суток пролежал в открытом файле на рабочем столе — в каталоге, который затем предлагалось импортировать в базу знаний. Доктор проверял базу, воркеров, бэкапы и эндпоинт модели, и не имел об этом никакого мнения.
- **Сравнение по точному значению, а не по шаблону.** Проверка знает, каковы учётные данные — они в окружении, с которым процесс запущен. Файл либо содержит этот токен, либо нет: подстраивать порог ложных срабатываний не нужно, и нет регулярного выражения, которое молча перестанет совпадать при смене формата токена.
- Два свойства неотменяемы, у каждого свой тест: **значение секрета никогда не попадает в отчёт** (детектор утечек, печатающий утечку, её расширил), и проверка **не может стать причиной медленной или упавшей диагностики** — обход ограничен глубиной 3, числом и размером файлов, а сбой подавляется.
- Резервные копии `.env.local` считаются лишними копиями и попадают в отчёт: сам конфиг — законное место для секретов, его бэкап — ещё одно место, откуда их можно потерять.
- Дорогая проверка включается флагом (`check_secrets`), как это уже сделано для проб эндпоинта: платят `doctor` и sentinel, а `status` и админский эндпоинт остаются быстрыми.

### Fixed

- Два дефекта в самой проверке, вскрытые прогоном на настоящем домашнем каталоге, а не на выдуманном: **`.env.local` отмечался как утечка** (файл, который и должен хранить секреты), и **каждая находка дублировалась**, потому что `JERICHO_HOME` лежит внутри `$HOME` и оба корня покрывают одно дерево.

### Документация

- Описаны все четыре команды, появившиеся сегодня и не упомянутые нигде: `jericho import`, `jericho events`, `jericho model-check`, `jericho eval-bootstrap`. Плюс разбор Inbox группами и гигиена секретов. Разделы `OPERATIONS.md` перенумерованы (было два раздела с номером 9).
- Каждая команда из документации проверена на существование в реальном CLI.

### Замеренное

- Обход настоящего `$HOME`: **1550 файлов за 0.33s**. На живом инстансе проверка нашла две лишние копии API-токена — резервные копии `.env.local`, оставленные сегодняшними правками; после уборки `doctor` чист.

### Compatibility

- Suite: **667 тестов** (+15); ruff/ruff format/mypy(99) ✓.

## 0.63.0 — 2026-07-26

0.63.0 — золотой набор можно начать: `jericho eval-bootstrap` предлагает кейсы из имеющихся знаний, а проверка честности отсеивает лёгкие.

### Added

- **`jericho eval-bootstrap`** (`--limit`, `--save`, `--user`). Кейсы оценки качества поиска майнятся из подтверждённого положительного фидбэка — источник правильный, но он не даёт ничего, пока систему не использовали. Свежий инстанс поэтому измеряет свой поиск по пустому набору вечно, и `eval_cases` стоял на нуле. Bootstrap спрашивает у модели, каким вопросом человек искал бы данный Knowledge Object; правильный ответ известен по построению — это тот объект, из которого вопрос сгенерирован.
- Кейсы сохраняются с источником `bootstrap`, чтобы набор, собранный моделью, никогда не спутали с собранным из реальных вопросов владельца.

### Проверка честности — это и есть функция

- **Опасность не в неверных ответах, а в лёгких.** Вопрос, написанный при взгляде на документ, повторяет его слова, и набор таких вопросов показывает отличный recall, проверяя только совпадение слов. Это не гипотеза: четыре кейса в собственном стенде этого проекта носили этикетку `cross-script`, делили с целевым документом до трёх содержательных слов и давали ровно **1.00** — завышая ту самую категорию, ради которой стенд и нужен.
- Поэтому каждое предложение проходит аудит на лексическое пересечение (не более одного общего слова) и на осмысленную длину. **На живой модели отсеяно 4 из 8** — все четыре пересказывали свой документ («checklist для технического релиза Jericho» против `RELEASE_CHECKLIST.md`). Без аудита сохранились бы все восемь.
- Отклонённое показывается с причиной и списком общих слов: аудит, который нельзя проверить глазами, доверия не заслуживает.
- **Ничего не сохраняется без `--save`.** Плохой золотой набор обесценивает все будущие измерения, так что это решение владельца, а не побочный эффект команды.

### Проверенное

- Полный цикл на настоящих данных: импорт 8 документов → продвижение → bootstrap → **встроенный `run_eval` отработал и выдал отчёт**, вместо того чтобы крутиться на пустом наборе.
- Сбой модели на одном объекте не валит пакет; ответ, проигнорировавший формат JSON, всё равно разбирается.

### Compatibility

- Схема БД не меняется (**16**), зависимостей ноль. Новый модуль `jericho/eval_bootstrap.py` и одна команда CLI.
- Suite: **652 теста** (+13); ruff/ruff format/mypy(98)/node --check ✓.

## 0.42.0 — 2026-07-25

0.42.0 — near-duplicate ищется по всему корпусу, а не по последним 1500 объектам.

### Fixed

- **Слепая зона дедупликации.** `detect_near_duplicates` брал **новейшие `JERICHO_DEDUP_MAX_OBJECTS` (1500)** векторов и сравнивал их между собой. Объект старше этого окна не был партнёром по сравнению **ни для кого** — а значит дубликат, приехавший позже, не находился никогда. Не «иногда позже», а никогда: усечение лишь писалось в `LOGGER.info`. На растущем корпусе фича молча переставала работать ровно тогда, когда становилась нужна. Тест, воспроизводящий дефект (старый объект + его дубликат за окном), закоммичен красным (`xfail(strict=True)`) и снят в этом же изменении.
- **Форма скана была неверной, и именно она порождала окно.** Полный all-pairs каждые 6 часов — это O(n²) на повторное сравнение пар, ответ по которым не менялся: замер на этой машине даёт **~23 с на 1500 объектов и ~17 минут на 10 000** в чистом Python. Теперь скан **инкрементальный**: каждый объект ровно один раз сравнивается со **всем** корпусом — сначала свежепроиндексированные векторы (новые данные важнее старого долга), затем нисходящий backfill истории по тайлу за тик. Курсор `(updated_at, knowledge_object_id)` живёт в `runtime_kv` и переживает рестарт. Бюджет тика (`JERICHO_DEDUP_SCAN_BATCH`=512, `JERICHO_DEDUP_SCAN_MAX_SECONDS`=600, делится между тенантами) теперь означает «догоним на следующем тике», а не «промолчим».
- **Ядро сравнения векторизовано** по образцу `dense_scores` из 0.38.0: `find_near_duplicate_pairs_against(probes, corpus)` с ветками numpy/чистый Python, идентичными решениями и тремя одинаковыми пропусками (нулевая норма, несовпадение размерности, self-пара). Обе ветки принимают упакованные float32-байты, поэтому расхождение по округлению невозможно. Замер блочного матмула: **1500 → 0.07 с, 10 000 → 0.41 с, 50 000 → 9.85 с**.

### Improved

- **Решённые пары больше не предлагаются заново.** `get_conflict_pair_statuses` читает карту `pair_key → status` **одним** запросом за прогон; пары в статусе `dismissed`/`resolved` отбрасываются **на этапе поиска**, а не после (иначе решённый кластер занимал бы места, на которые претендует по-настоящему новый дубликат), счётчик `suppressed`. `confirmed` намеренно не фильтруется: повторное касание лишь поднимает confidence. (Оговорка: полное перечитывание конфликтов внутри `store_knowledge_conflict` — `storage:3374` — при этом **остаётся**, по одному на записанную пару; ревью справедливо поймало это как неточность в первой редакции этой записи.)
- **Наблюдаемость вместо молчания.** Ответ детектора теперь несёт `objects_compared`, `mode` (`incremental`/`backfill`), `pending` (сколько объектов ждёт первого полного сравнения), `suppressed`, `incomplete` и `elapsed_sec`; `objects_scanned` впервые означает то, что подразумевал тост админ-UI, — размер корпуса. Ключ `truncated` **удалён**: он уезжает в `audit_log.after_json`, а его смысл при инкрементальном скане инвертировался бы — держать в append-only аудите одно имя с двумя несовместимыми смыслами хуже, чем переименовать.
- **Воркер и эндпоинт.** Бюджет тика делится между тенантами, поэтому скан не может выродиться в повторяющийся `timeout` в `workers:health:knowledge_dedup` (`asyncio.to_thread` **не прерываем**: таймаут супервизора снимает корутину, а поток продолжает считать). Ручной `POST /api/admin/knowledge/detect-duplicates` ушёл с event loop в поток и принимает `full_rescan` для пересканирования истории по требованию.
- **Порог перечитывается каждый прогон**: его **понижение** сбрасывает курсор (ранее отвергнутые пары стали годными, хотя ни один вектор не двигался), повышение — нет.
- **По adversarial-review** (3 линзы × verify-проход; 13 находок, 5 подтверждено, 7 отклонено, 1 осталась без вердикта из-за обрыва связи — проверена вручную и оказалась настоящей) исправлено 6 дефектов, каждый закрыт регрессионным тестом, проверенным на падение без своей починки:
  - **Скан мог встать навсегда** (HIGH→MED): курсор страницы внутри развёртки — локальная переменная, поэтому прерванная по дедлайну развёртка выбрасывалась и переигрывалась один в один. Если одна плитка против корпуса стоит дороже одного бюджета, ни одна плитка не завершалась бы **никогда** — ноль продвижения на каждом тике. Воспроизведено ревьюером дважды на реальном хранилище. Теперь **первая плитка прогона всегда доводится до конца**, а прогон, не продвинувшийся ни на объект, пишет **warning**, а не тонет в тишине.
  - **Неограниченный накопитель пар** (HIGH, та самая находка без вердикта): ядро возвращало **список** всех пар выше порога — на кластере дубликатов это квадратично. Замер: одна плитка из 512 проб против 5000 одинаковых записей — **2.56 млн пар и 332 МБ** ещё до единой записи в БД, при том что сохранить можно максимум 200. Ядро стало **генератором**, потребитель держит кучу фиксированного размера: те же входные данные — **35 МБ** (−90%), и остаток теперь занимают сами векторы страницы.
  - **`dedup_scan_batch` выше лимита страницы** (MED): хранилище молча урезает запрос до 10000, а короткая страница читалась как «история кончилась» — всё старше первых 10000 строк не проверялось бы никогда. Размер плитки клампится по фактическому лимиту, а конец истории определяется **только по пустой** странице.
  - **numpy и чистый Python расходились на границе порога** (MED→LOW): numpy-ветка считала в float32 (дрейф ~1.5e-8 виден в тесте), Python — в float64, из-за чего пара могла оказаться по разные стороны гейта в зависимости от наличия опционального extra. Обе ветки теперь float64.
  - **Гонка за состояние скана** (MED→LOW): тик воркера и ручной запуск из админки перекрываются, а состояние — read-modify-write одного блоба на весь прогон. Слияние сделано консервативным: берётся более дальний курсор, а «история пройдена» ставится, только если **обе** стороны согласны — проигравший может стоить лишней работы, но не покрытия.
  - **Шаг часов назад** (LOW): строка со штампом ниже водяного знака навсегда пряталась за строгой границей `after`. Теперь при завершённой истории запоминается число строк под знаком, и его рост **переоткрывает backfill**.
- **Отступление от плана, сделанное осознанно.** Синтезированный дизайн предлагал ранний обрыв по Коши–Буняковскому в чистом Python, обосновывая это тем, что «numpy на этой машине нет». Это оказалось ошибкой измерения: судья опрашивал системный `python3`, тогда как Jericho запускается из `.venv/bin/python`, где **numpy 2.5.1 установлен**. Оптимизация вырезана: она ускоряет неосновной путь ценой приближения с ранним выходом, которое пришлось бы отдельно доказывать как «решения не меняются».

## 0.33.0 — 2026-07-24

0.33.0 — переархитектура хранилища: соединение-на-поток + WAL. Устранён hazard общего sqlite-курсора (корректность, не только латентность).

### Fixed

- **Hazard общего sqlite-соединения (полу-записанные чтения).** `JerichoStorage` держал ОДНО `sqlite3.Connection` (`check_same_thread=False`) под RLock, удерживаемым только вокруг `conn.execute()` — а `.fetchone()/.fetchall()` шли уже ПОСЛЕ отпускания замка (~140 мест). Фоновые воркеры (через `asyncio.to_thread` на потоках пула) шагали курсорами по тому же соединению одновременно с обработчиками запросов — документированный hazard («recursive use of cursors» / полу-записанные строки): `quality_score=None` → `TypeError`, каскадный hard-purge общего Raw Object. Теперь **соединение-на-поток** (`threading.local()`): два потока никогда не делят одно `sqlite3.Connection`, курсоры не пересекаются, а WAL даёт много одновременных читателей + одного писателя. Публичный API (`execute/transaction/commit/close/conn`) не изменился, поэтому ~140 мест вызова не трогались. Repro старой модели даёт `AssertionError`/`IndexError: tuple index out of range`; новая модель — 0 ошибок под нагрузкой (8 писателей × 8 читателей, 6/6 прогонов).

### Improved

- **Одноразовая миграция за барьером + пер-соединенческая настройка.** Схема/миграция/FTS теперь выполняются РОВНО один раз (первое соединение) под `_init_lock` с двойной проверкой `_schema_ready`; остальные соединения только открываются и настраиваются. Пер-соединенческие настройки (`row_factory`, `busy_timeout`, `journal_mode=WAL`, **`foreign_keys=ON`** — не persistent!, `synchronous=NORMAL`, UDF `jericho_casefold`) применяются на КАЖДОМ соединении. `busy_timeout` нормализуется к 10000 после миграции (CORE_SCHEMA временно понижал до 5000).

## 0.27.0 — 2026-07-24

0.27.0 — исправления по итогам грунтованного аудита: два реальных бага (целостность + доступность) и два усиления качества ответов.

### Fixed

- **Бэкап больше не морозит сервер во время верификации.** `create_backup` держал единственный глобальный storage-lock на протяжении всего `integrity_check` + `foreign_key_check`, хотя те идут по отдельному соединению к КОПИИ и лок им не нужен — каждый Telegram/Admin-запрос вис на весь (потенциально минутный) скан при ежечасном бэкапе. Теперь лок держится только на `checkpoint` + `.backup()`; проверка вынесена в `_verify_backup_conn` вне лока. Конкурентный тест: читающий вызов не блокируется во время верификации.
- **Конкурентные подтверждения Inbox больше не создают дубли KO.** `classify_inbox_item` читал `knowledge_object_id` из устаревшей строки, затем создавал KO и флипал статус разными транзакциями без guard'а — два одновременных подтверждения (админка + Telegram + воркер) оба продвигали, порождая два canonical KO из одного Raw Object. Теперь: сохранить KO → атомарный CAS-claim слота (`claim_inbox_promotion`, `WHERE knowledge_object_id IS NULL`); проигравший purge'ит свой сирота-KO и adopt'ит победителя. Инвариант «Inbox → canonical ровно один раз» защищён 4-поточным тестом.

### Improved

- **Query-aware сниппеты.** В контекст модели клался `summary`/первые 520 символов `content` — никогда область, реально сматчившаяся запросом, из-за чего в длинных заметках доказательство уходило за кадр (ответ не заземлялся, верификатор ложно предупреждал). `retrieval.best_snippet(query, text)` — чистый, без модели, скоринг окна по общему токенайзеру — выбирает пассаж с максимумом различных токенов запроса; используется для excerpt каждого KO.
- **Верификатор проверяет процитированное.** `_verify_response` судил ответ по `knowledge_hits[:5]` (обрез 300 символов), игнорируя, какие `[K#]` ответ реально процитировал. Теперь evidence строится из процитированных KO (query-aware сниппеты), fallback на top-hits только если не процитировано ничего.

### Security

- **Аудит провалов аутентификации.** HTTP-граница не оставляла durable-следа при провале: bad/revoked bearer, битая подпись моста, replay nonce, запрещённый чат, capability-denial (403), lockout (429) — только in-memory счётчик. После утечки токена (SECURITY §10) невозможно было увидеть факт/время/IP злоупотребления. Теперь каждая failure-ветка middleware пишет append-only событие `auth.failed` (reason-код, status, method, path, IP, request_id — **только метаданные, никогда сам секрет**); user_id=`anonymous` для неаутентифицированных. Видны в существующей admin-вьюхе аудита.

### Notes

- Отложено намеренно: переход storage на соединение-на-поток (корневая concurrency-модель) — заслуживает отдельной сессии со стресс-тестом; частичный фикс (обернуть чтения воркеров в `to_thread`) без него лишь усилил бы cursor-гонку на общем соединении.
- Схема БД не меняется (14). Ноль новых зависимостей. Suite: **372 теста**; ruff/mypy(44)/bandit(0 HIGH) ✓. Работа велась на ветке `fixes/audit-tier0`.

## 0.9.4 — 2026-07-22

0.9.4 делает семантический поиск функциональным. Раньше embeddings только пере-ранжировали пул FTS+recency и нигде не сохранялись, поэтому смысловое совпадение без общих слов и не из числа недавних было недостижимо. Теперь векторы индексируются и хранятся, а поиск ведёт полноценный dense recall по всему корпусу.

### Added

- **Персистентный векторный индекс.** Новая таблица `knowledge_embeddings` (float32-вектор в BLOB, модель, размерность, `source_version`, `content_hash`) хранит по одному актуальному вектору на Knowledge Object. Схема БД 9 → 10.
- **Воркер индексации `embeddings_index`.** Периодически (по умолчанию каждые 120 c, `JERICHO_EMBEDDINGS_INDEX_INTERVAL_SEC`) эмбеддит батч объектов, у которых вектор отсутствует, из другой модели или устарел по версии объекта. Новые/переобогащённые объекты становятся доступны семантическому поиску в течение одного цикла; сбой бэкенда просто откладывает батч.
- **Corpus-wide dense recall.** Запрос эмбеддится один раз, косинусно сравнивается со всеми сохранёнными векторами пользователя, и сильнейшие совпадения объединяются с пулом кандидатов до ранжирования — смысловое совпадение без общих токенов и не из недавних теперь находится и проходит через evidence-gate.
- Ручки: `JERICHO_EMBEDDINGS_INDEX_BATCH` (64), `JERICHO_EMBEDDINGS_INDEX_INTERVAL_SEC` (120), `JERICHO_EMBEDDINGS_RECALL_CANDIDATES` (40); блок `embeddings` в `public_dict` для диагностики.

### Changed

- Dense-сигнал в поиске теперь берётся из сохранённых векторов, а не пересчитывается для всего пула при каждом запросе. Пока индекс пуст (embeddings только включили), поиск мягко деградирует к прежнему поведению — эмбеддингу текущего пула.
- Векторы, чьи объекты мягко удалены, исключаются из recall; смена активной модели/размерности инвалидирует старые векторы (индекс их пересоберёт).

### Compatibility

- Ноль новых зависимостей: векторы упаковываются через `array`/`struct`, косинус считается на чистом Python (подходит для персонального масштаба).
- Требуется локальный OpenAI-совместимый embeddings-эндпоинт: задайте `JERICHO_EMBEDDINGS_ENABLED=1`, `JERICHO_EMBEDDINGS_BASE_URL` (обычно ОТДЕЛЬНЫЙ от chat-vLLM сервис с `/embeddings`) и `JERICHO_EMBEDDINGS_MODEL`. Без этого поиск работает как прежде (лексика+FTS+граф+lifecycle).

## 0.9.1 — 2026-07-22

0.9.1 закрывает дыры «открытого бота» в Telegram-контуре: deny-by-default для чатов, одноразовые nonce против повторного воспроизведения запросов и явная загрузка владельца. Изменение поведения намеренное и требует конфигурации при обновлении.

### Security

- **Deny-by-default для Telegram**: пустой список чатов больше НЕ означает «пускать всех». Бот принимает только чаты из эффективного allowlist = `JERICHO_TELEGRAM_ALLOWED_CHAT_IDS` ∪ `JERICHO_TELEGRAM_OWNER_CHAT_IDS`. Исправлено во всех трёх гейтах (мост: сообщения и callback; backend: аутентификация). Backend отвечает 403 (а не 401), поэтому мост сразу отбрасывает неавторизованный чат, а не повторяет запрос сотни раз.
- Новая настройка `JERICHO_TELEGRAM_OWNER_CHAT_IDS` — чаты владельца, которые всегда разрешены (bootstrap без ручного заполнения allowlist).
- `validate_settings` теперь требует непустой allowlist/owner при заданном bridge secret: жёсткая ошибка запуска в production (не-loopback bind), предупреждение в loopback-разработке. `jericho telegram-bridge` тоже проверяет это перед стартом, а `TelegramConfig.validate()` отказывается запускать открытый бот.
- **Одноразовый nonce** в HMAC-подписи запросов моста: подпись расширена полем `nonce`, backend хранит короткоживущий кэш увиденных nonce (в `runtime_kv`, чистится фоновым worker-ом) и отклоняет повтор внутри окна свежести. Легитимные повторы моста используют новый nonce и не блокируются.

### Compatibility

- **Поведенческое изменение**: развёртывания, полагавшиеся на пустой allowlist (открытый бот), после обновления перестанут отвечать, пока не задан `JERICHO_TELEGRAM_ALLOWED_CHAT_IDS` или `JERICHO_TELEGRAM_OWNER_CHAT_IDS`. В production backend не стартует без этого.
- Формат подписи моста изменён (добавлен nonce). Мост и backend деплоятся вместе; согласование версий не предусмотрено — обновляйте оба компонента одновременно.
- SQLite schema не меняется (остаётся **9**): кэш nonce хранится в существующей таблице `runtime_kv`.

0.6.1 заменяет первоначальную сборку 0.6.0 и является результатом независимого adversarial release-аудита. Архитектура и продуктовая политика 0.6 сохранены; выпуск закрывает найденные границы доверия, конкурентные гонки и ресурсные риски.

### Fixed

- Закрыт обход loopback-owner authentication через поддельный `X-Forwarded-For`: proxy headers принимаются только от явно доверенного непосредственного proxy-hop, цепочка проверяется справа налево, а Uvicorn не переписывает peer до application validation.
- Web fetch защищён от DNS rebinding: соединение устанавливается с уже проверенным публичным IP при сохранении исходных Host/TLS SNI; каждый redirect проходит новую проверку.

- Одновременная первая инициализация SQLite получила bounded retry, а core schema migration стала единой транзакцией. Неизвестная более новая schema version отклоняется fail-closed без частичных изменений.
- Явное «не запоминай / do not remember» имеет абсолютный приоритет над `force_knowledge` и для текста, и для документа: долговременный след и файл не создаются.
- Динамические Knowledge Objects, граф, query, вложения и suggestions больше не попадают в system-role модели; они передаются как недоверенный JSON data block на user-role boundary.
- Telegram читает вложение потоково и прекращает download сразу после byte limit; `/start`, `/help`, пустой `/note` и неподдерживаемый первый контакт регистрируют пользователя через подписанный backend probe.
- Permanent backend conflicts больше не повторяются до исчерпания многодневного retry budget, а остаются диагностируемым dead-letter.
- HTTP body limiter считает фактически принятые байты, включая chunked transfer, до auth/JSON/multipart parsing.
- Admin API возвращает строгие `400` для malformed/non-object JSON, non-finite/out-of-range чисел, псевдобулевых строк и неизвестных graph-link status вместо внутренних `500` или неявного coercion.

- Backup verification требует корректный manifest и сверяет путь, filename, size, SHA-256, schema version и SQLite integrity.

### Changed

- Entity extraction стала консервативной и перестала склеивать границы предложений.
- Workers выполняют обслуживание для всех активных пользователей и не принимают uncertain решения.
- Code execution выключен по умолчанию, скрыт от модели без capability и явно не позиционируется как security sandbox.
- Runtime artifacts, БД, WAL/SHM, caches и secrets исключены из дистрибутива.
- Добавлена идемпотентная миграция pre-release SQLite-схемы: пользователи, provenance hashes, version snapshots, Inbox links и FTS восстанавливаются без потери знаний.

### Security

- Default-deny permissions.
- HMAC request authentication для Telegram bridge.
- Rate limits, strict CORS validation, security headers.
- Cross-tenant administrative mutations требуют `admin.all_data.manage`.
- Web fetch блокирует private network targets и проверяет redirects/DNS.
